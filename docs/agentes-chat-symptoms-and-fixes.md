# agentes.chat — 증상과 해결책

2026-11-17 기준. 각 항목은 **증상 → 원인 → 해결(즉시 우회 / 근본 수정) → 확인 방법** 순서입니다.
실제 코드에서 확인한 사실만 적었고, 확인 못 한 것은 UNVERIFIED로 표시했습니다.

---

## 1. OpenRouter 모델이 에이전트 모델 선택기에 안 보인다

**증상** 워크스페이스에 OpenRouter 키를 넣었는데 에이전트 brain/모델 목록에 OpenRouter 모델이 없다.

**원인** OpenRouter는 고정 카탈로그에 없고, **키가 살아있을 때만 런타임에 목록을 받아 메모리에 채우는** 구조다.
게이트는 `GET /api/app/models` → `pickerModels()` → `openRouterInUse(db)`(키 존재 확인) → `ensureOpenRouterModels()`.
그런데 클라이언트가 `/models`를 10분간 캐시(`staleTime`)하고 포커스 리페치가 꺼져 있어, **키 추가 전에 목록을
불러온 브라우저는 계속 빈 목록**을 본다. 목록 읽기가 실패하면 60초 백오프 동안 재시도도 하지 않는다.

**해결**
- 즉시: 시크릿 창(새 브라우저 세션)으로 열거나 10분 기다린 뒤 새로고침, 키 저장 후 서버 재시작.
- 근본: 픽커의 `/models` 쿼리를 항상 리페치하도록 바꾼다(`staleTime`을 0으로). 서버측만 고치려면
  `openRouterInUse` 캐시를 제거한다.

**확인** 브라우저 네트워크에서 `/api/app/models` 응답에 `provider: "openrouter"` 항목이 있는지, 그 뒤 픽커에
노출되는지 본다.

## 2. OpenRouter 모델에 이미지를 보냈는데 못 읽는다

**증상** 이미지 첨부해도 모델이 이미지를 인식하지 못한다(텍스트만 처리).

**원인** OpenRouter 경로가 **모든 모델에서 이미지 파트를 무조건 제거**하고 텍스트만 보낸다. 코드에 그렇게
적혀 있고(“images left out for every model…”) 모델별 능력 정보를 쓰지 않는다. 실제로 OpenRouter `/models`는
`architecture.input_modalities`에 `image` 여부를 주고 있으므로 **데이터는 있는데 안 쓰는 상태**다.

**해결**
- 즉시: 이미지가 꼭 필요하면 그 모델을 **직접 프로바이더(OpenAI/Anthropic/Google 키)로** 붙인다.
- 근본: 모델별 이미지 능력을 읽어, 그 능력이 있는 모델만 이미지를 통과시킨다(능력 정보가 없는 모델은
  기존처럼 제거 — 안전한 기본값 유지).

**확인** 이미지를 넣고 응답이 이미지 내용을 언급하는지. 텍스트 전용 요청이 그대로 동작하는지도 함께 확인.

## 3. “메인 세션에는 컴퓨터를 추가할 수 없다”

**증상** 기본 어시스턴트(오른팔) DM에서 컴퓨터 추가 버튼이 없거나 API가 거절한다.

**원인** **의도된 설계**다. 코드에 “The team's right hand can't be given a computer” 가드가 있고, DM 헤더에서
버튼 자체를 렌더하지 않는다.

**해결** 컴퓨터가 필요한 작업은 **일반 에이전트 DM** 또는 **mission**에서 한다. mission은 생성 시 컴퓨터를
스냅샷하고 이후 에이전트 설정 변경을 따라가지 않는다. 오른팔에게도 컴퓨터를 주려면 코드 변경(가드 + UI
조건)이 필요하다.

**확인** 일반 에이전트 DM에서 `PUT …/agents/{id}/computer/target` 흐름이 성공하는지.

## 4. 컴퓨터를 연결했는데 붙지 않는다 / 붙었는데 실행이 안 된다

**증상** 기기 연결 코드를 넣었는데 target이 안 잡히거나, 잡혀도 턴이 실패한다.

**원인** 붙이는 것과 실행되는 것은 별개다.
- 붙이기: `pair_computers` 권한 필요, 코드는 10분 만료·IP당 10개 한도, **온라인일 필요는 없다**.
- 실행: 오프라인/일시정지면 턴이 `machine_offline`/`machine_paused`로 실패한다. 권한은 `manage_agents` 또는
  그 에이전트의 owner여야 하고, **남이 연결한 컴퓨터는 붙일 수 없다**(직접 페어링한 것만).

**해결** 머신이 온라인인지, 내가 owner/admin인지, 내가 페어링한 컴퓨터인지 확인. Cloud/외부 프로비저닝
환경이면 픽커가 숨겨지고 `device.not_home`으로 거절된다.

**확인** `dori`가 아니라 agentes.chat 설정의 Devices 목록에서 상태 확인 후 target 지정을 다시 시도.

## 5. GitLab을 쓰고 싶은데 clone/push가 안 된다

**증상** Connectors에 GitLab이 보여 연결했는데, 에이전트가 저장소를 clone하거나 push하지 못한다.

**원인** 두 층이 다르다.
- **Connectors의 GitLab = Composio 툴킷**(약 300개 API 도구: 이슈, MR, 커밋 생성, 파일 생성 등). 도구 호출이지
  git이 아니다.
- **git 프록시는 GitHub 전용**으로 하드코딩돼 있다(대상 호스트가 github.com/api.github.com).

**해결**
- 대부분의 경우: **연결된 컴퓨터에서 GitLab으로 직접 clone**한다(SSH deploy key 또는 프로젝트 액세스 토큰,
  `read_repository`/`write_repository`). 프록시는 “클라우드 샌드박스에 토큰을 넣지 않으려고” 만든 장치라,
  통제된 사내 머신에는 해당이 없다.
- 클라우드 컴퓨터를 쓴다면 프록시에 GitLab 어댑터가 필요하다(연결 타입 + 호스트/인증 해석 + GitHub 경로 불변).

**확인** 컴퓨터에서 `git clone https://gitlab.사내/…`가 토큰/키로 성공하는지, 그 뒤 push까지 되는지.

## 6. 리즈닝(reasoning) 설정이 안 보인다

**증상** 모델을 골라도 effort 단계 선택 UI가 없거나 비어 있다.

**원인** 모델의 `supported_efforts`가 목록에 없으면 선택지가 비어 있다(`null`이면 전 단계, 배열이면 그 안에서만,
필드가 없으면 선택 불가). 리즈닝 토큰은 **출력으로 청구**되므로 effort를 항상 최대로 두면 비용이 커진다.

**해결** effort를 지원하는 모델을 고르거나, 지원 정보가 있는 모델로 바꾼다. 사고가 강제되는 모델은 `none`을
보내도 무시될 수 있다.

**확인** 픽커에서 effort 픽셀이 뜨는지, 실행 후 usage에 reasoning 토큰이 잡히는지.

## 7. 개인 키가 다른 사람에게 안 보인다 (버그인가?)

**증상** 내가 등록한 API 키가 동료 화면에는 안 보인다.

**원인** **의도된 설계**다. 모델 자격증명은 org 스코프로 저장되고, 개인 계정은 소유자에게만 값이 렌더된다.
조직 키도 비관리자에게는 상세가 숨겨진다. 실행 크레딧은 “머신에 연결된 계정” 기준으로 잡힌다(대화한 사람
기준이 아님).

**해결** 팀 공용 에이전트는 **워크스페이스 키 + 공용 컴퓨터**, 개인 실험은 **내 계정 + 내 컴퓨터**로 분리한다.
개인 키를 전체에 쓰게 하려면 그 토글을 켠다(권장하지 않음).

**확인** Settings → AI accounts에서 계정별 scope 표시 확인.

## 8. 리뷰(게이트)가 리드를 오래 붙잡는다 — dori 운영

**증상** 레인 리뷰가 끝날 때까지 리드 세션이 아무 일도 못 한다.

**원인** 리뷰가 리드 팬에서 동기 실행되고, 큰 diff는 청크 여러 개 × 최대 600초가 걸린다.

**해결** 리뷰를 리드의 in-process 서브에이전트로 돌린다: `dori review --lane <key>`가 요청과 diff만 기록하고 `QUEUED`를 찍으며, 리드가 `omo-native-gate-reviewer` 서브에이전트 하나로 판정한 뒤 `dori review <key> --attest --verdict ... --reviewer ... --evidence ...`로 영수증을 쓴다. duty는 리뷰어를 띄우지 않고 요청 상태·만료만 보고한다. `dori done`은 진행 중이면 즉시 “요청 대기 중”으로 거절하고 블로킹하지 않는다.

**확인** `dori review --lane x`가 즉시 `QUEUED …`로 끝나는지, attest 후 `receipts/lane_<key>@<tip>.json`이 생기는지 확인한다.

## 9. 기본 리뷰어가 403 `Model access is disabled`

**증상** 리뷰어 서브에이전트가 매번 403으로 끝나고, 그 verdict를 attest한 영수증이 `reviewer_empty`로 남는다.

**원인** 그 모델의 **접근 권한이 꺼져 있다**(레이트리밋 아님). 재시도해도 같은 결과다.

**해결** 접근 가능한 모델을 리뷰어 서브에이전트에 지정한다(현재 glm 계열로 고정해 사용 중). 서브에이전트의 모델과 오류로 확인 가능.

**확인** 서브에이전트의 리포트와 `receipts/lane_<key>@<tip>.json`의 `reviewer`·`verdict` 필드.

---

## 10. 4시 자동 업데이트가 돌았는지 궁금할 때

**증상** 밤사이 업데이트가 실행됐는지 모르겠다.

**원인/확인** `state/update-check.log`의 **파일 수정 시각**과 로그 라인을 본다. 새로 설치할 게 없으면 라인이
남지 않을 수 있으므로 mtime이 판단 근거다. 다음 실행 시각은 `state/update-check-next`(epoch ms)로 확인한다.

## 부록 — 지금 우리 환경의 고정 값

- 리뷰어 기본값: `reviewModel` = glm 계열, 실패 시 대체 모델은 `reviewFallbackModel`.
- 사내 GitLab 경로: **커넥터(API) + 컴퓨터 직접 clone**. 클라우드 컴퓨터를 쓰기 전에는 프록시 어댑터 불필요.
- 모델 키는 org 레벨, 개인 키는 실험용. 예산은 에이전트별로 분리.
