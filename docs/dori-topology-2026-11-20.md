# 도리 토폴로지 정리 (2026-11-20)

Lee 지시: "도리를 쓰고, up.computer를 쓰고, 도리를 프로젝트마다 키고, 메인 도리는 메시징 툴을 쓴다."

## 1. 3층 구조

```
[메시징]  Discord (지금) → 사내 채팅(Zulip/Mattermost, 이후)
   │  대화·승인 요청·보고
   ▼
[메인 도리]  한 사람당 1개. $DORI_HOME = ~/.dori
   │  · 백로그(무엇을 언제 시킬지) · 게이트 승인 · 프로젝트 간 조정
   │  · up.computer에 뜨는 '나' (ACP 프로바이더)
   │
   ├── ssh/ACP ──▶ [프로젝트 도리 A]  DORI_HOME=~/projects/A/.dori
   ├── ssh/ACP ──▶ [프로젝트 도리 B]  DORI_HOME=~/projects/B/.dori
   └── ssh/ACP ──▶ [프로젝트 도리 C]  (다른 머신일 수도)
         │  그 프로젝트의 레인·리뷰·라벨 상태를 소유
         ▼
       [git 원격]  local/<machine>/<key> 브랜치 = 결과물 전달 경로
```

- **메시징** = 사람과 메인 도리의 창구. 지금은 Discord, 회사는 Zulip/Mattermost 후보(미국은 Slack 브리지).
- **메인 도리** = 사령부. 백로그·승인·조정만. 직접 코드 작업은 프로젝트 도리로 넘긴다.
- **프로젝트 도리** = 해당 리포의 실행 주체. 레인·워크트리·리뷰 영수증·`status:*` 라벨을 그 리포 안에서 소유.
- **up.computer** = 셸. 메인/프로젝트 도리를 ACP 프로바이더로 붙여 채팅·태스크·워커 화면을 제공. 상태는 소유하지 않는다.

## 2. 상태 경계 (중요)

| 무엇 | 어디가 진실원 |
|---|---|
| 레인·워크트리·리뷰 영수증 | **각 프로젝트 도리**의 `$DORI_HOME/state` |
| 백로그·승인 대기·게이트 | **메인 도리** |
| 코드·PR·라벨 | **리포지토리**(git, `status:*` 라벨) |
| 대화·보고 | 메시징 채널 |

프로젝트 도리와 메인 도리 사이에 **공유 상태 파일은 두지 않는다.** 오가는 것은 ① 브리프 ② `local/<machine>/<key>` 브랜치 ③ 영수증 요약(텍스트)뿐.

## 3. 요청 흐름

1. 사람이 메시징에서 메인 도리에게 요구 → 메인 도리가 **백로그 항목**으로 만든다(브리프 파일).
2. 메인 도리가 해당 **프로젝트 도리**에게 브리프를 전달 — 같은 머신이면 `dori send`/ACP, 다른 머신이면 `dori remote start`.
3. 프로젝트 도리가 레인을 열고 작업 → 리뷰 게이트 → 커밋/브랜치.
4. 결과는 `local/<machine>/<key>`로 회수되거나 PR로 승격. 영수증 요약이 메인 도리로 돌아온다.
5. 사람이 메시징에서 승인 → 메인 도리가 머지/다음 항목 결정.

## 3.5 코딩 중 흐름 (Lee 확정: 사람은 프로젝트 도리와 작업하고, 메인 도리는 듣고 넘긴다)

- **사람 ↔ 프로젝트 도리**: up.computer 스레드가 프로젝트 도리의 ACP 세션에 붙어 **직접 코딩 대화**. 여기가 손을 움직이는 자리.
- **메인 도리는 옆에서 듣는다**: 프로젝트 도리의 세션 기록(JSONL)을 **꼬리 읽기**해서 무슨 일이 오갔는지 요약한다(대화를 끊지 않고).
- **메인 도리가 넘긴다**: 대화에서 드러난 "이것도 해야 한다"를 백로그 항목/브리프로 바꿔 **프로젝트 도리에게 전달**(같은 머신이면 `dori send`, 아니면 `dori remote start`).
- **사람은 메시징에서 승인만**: 결과·게이트·결정만 메인 도리와 주고받는다. 코딩 맥락은 프로젝트 도리에만 둔다.

필요한 새 부품(아직 없음):
1. **세션 tailer**: 프로젝트 도리 세션 파일을 읽어 요약·항목 후보를 만드는 잡(분 단위).
2. **이중 보고 금지 규칙**: 사람이 이미 프로젝트 도리와 합의한 내용을 메인 도리가 다시 묻지 않도록, 요약을 근거로만 쓴다.
3. **루프 라우팅**: 메인 도리 대화에서 "어느 프로젝트인가"를 판정하는 규칙(기본값: 최근 대화한 프로젝트).

## 3.6 다채널 인박스 (메인 도리는 나만 듣지 않는다)

메인 도리의 입력은 Discord 하나가 아니다. 회사 채팅(Zulip/Mattermost), 미국 Slack 브리지, 이메일/웹훅까지 같은 큐로 모아야 한다.

- **Inbound 정규화**: `{source, channelId, threadId, author, text, attachments, ts, replyTo, isOwner}` 한 형태로 `state/channel-inbox.jsonl`에 적재.
- **어댑터(수집)**: Discord(현재 구현), Zulip(이벤트 큐), Mattermost(WebSocket), Slack(브리지). 어댑터는 **읽기 전용 수집기**이고 판단은 하지 않는다.
- **라우터(메인 도리)**: 큐를 드레인 → 우선순위(⬇ 소유자 > 팀 > 알림) → 프로젝트 라우팅 → 답변 생성 → **origin으로 회신**.
- **Outbound**: `{source, threadId, text, files, replyRef}`. 채널별 규칙을 지킨다(Discord는 reply 참조·인용 금지, Zulip은 topic 유지, Slack은 thread).

지켜야 할 것:
1. **중복 금지**: 한 메시지는 한 번만 처리(채널별 last-id 체크포인트).
2. **비용 가드**: 모든 채널을 원문으로 컨텍스트에 넣지 않는다 — 채널별 요약 + 필요 시 원문 조회.
3. **권한**: 소유자가 아닌 사람의 요구는 자동 실행 금지(백로그 제안까지만).

현재 갭: 채널 추상화가 없다(`src/plugins/discord.ts`가 Discord 전용). `src/channels/types.ts` + `discord.ts`(기존 래핑) + `state/channel-inbox.jsonl`이 첫 조각이고, Zulip/Mattermost는 회사 채팅 결정 후 하나만 만든다.

## 3.7 다른 머신: 경량 데몬만 (2026-11-20 확정)

다른 머신에 **dori 전체를 설치하지 않는다.** 그 머신에는 실행만 하는 얇은 데몬을 두고, 두뇌는 이쪽에 둔다.

**데몬이 하는 일 (그리고 하지 않는 일)**
- 한다: 세션 생성/종료, 터미널 스트림, git fetch/checkout/worktree, 파일 읽기·쓰기.
- 안 한다: LLM 호출, 백로그, 승인 판단, 상태 소유. (두뇌가 둘이 되면 상태가 갈라진다)

**이미 있는 후보**
1. **herdr 원격 서버** — `herdr machine add <ssh>`가 원격 herdr 서버를 준비한다(계정 없음, ssh 기반). dori는 `--machine` 플래그만 넘기면 되고, 빠진 것은 **원격 worktree 생성 로직**뿐.
2. **자체 `dori-agent` 데몬** — Bun 단일 바이너리: HTTP+WS로 `session create/exec/kill`, `git worktree add/remove`, `file read/write`. 500줄 규모. herdr 없이도 동작.

**권장**: 1번을 먼저(이미 검증된 데몬을 재사용), worktree 처리만 dori 쪽에 추가. herdr 의존을 없애고 싶을 때 2번을 만든다.

**결과**: 새 머신 준비물 = `ssh + git + bun`(+herdr 또는 dori-agent)뿐. dori 홈·백로그·게이트는 이쪽에만 존재한다.

**변형 (2026-11-20, Lee 제안): 원경에 '도리'가 아니라 'omo'만 돌린다**

데몬조차 필요 없다는 더 얇은 안. 원경에는 **이미 있는 에이전트 CLI(omo/omp)**만 있으면 된다.

```
ssh <host> 'cd <repo> && git worktree add ../wt-<key> -b local/<host>/<key> \
  && cd ../wt-<key> && omo -p "$(cat /tmp/<key>.md)"'
```

- **omo는 이미 비대화 모드**를 갖고 있다: `--print, -p` ("process prompt and exit"), `--mode json|rpc` — 즉 완료 판정은 종료코드/JSONL로 가능.
- 원경에 필요한 것: `git + bun + omo`(+모델 자격증명). **dori 설치는 불필요**.
- 레인 의미는 이쪽이 계속 소유: 부리프 생성, 원경 worktree 생성 지시, 완료 감시, 브랜치 회수, 영수증.
- 잃는 것: 원경 pane을 실시간으로 보는 것(로그 테일로 대체). 얻는 것: 원경 준비물이 극단적으로 줄고 두뇌가 하나로 유지됨.

**권장 순서**: 이 변형을 `dori remote start --engine omo`로 먼저 구현(현재 ssh 버전 수정). 그 다음 필요하면 herdr `--machine`으로 '보는 것'을 추가.

## 4. 지금 있는 것 / 없는 것
- 메인 도리: 백로그, 루프, 게이트, `dori remote`(ssh), Discord 게이트웨이
- 프로젝트 격리: `DORI_HOME` 환경변수(별도 홈 = 별도 상태)
- 셸 연동: `dori acp` (ACP 프로바이더로 등록 가능)
- 결과 전달: git 브랜치 규약

**없음 (필요하면 만든다)**
- **프로젝트 도리 목록/상태 조회**: 메인 도리가 "A는 지금 뭐 하고 있나"를 직접 못 본다 → `dori remote list` 확장 또는 각 프로젝트가 자기 상태를 요약해 허브에 푸시
- **메시지 라우팅**: 메인 도리 대화에서 "이건 A 프로젝트 일"을 자동 분기하는 규칙
- **up.computer 다중 프로바이더 등록 자동화**: 프로젝트마다 ACP 엔트리를 손으로 추가해야 함
- **승인 게이트 통합**: 프로젝트 도리 게이트를 메인 도리 인박스로 모으는 경로

## 5. 결정해야 할 3개

1. **프로젝트 도리의 범위**: 리포 1개 = 도리 1개인가, 아니면 '제품' 단위(여러 리포)인가. (권장: 리포 1개, 필요하면 상위 도리)
2. **메인↔프로젝트 연결 방식**: ① 같은 머신의 프로세스로(ACP/`dori send`) ② ssh(`dori remote`) ③ 둘 다(머신에 따라). 권장: 둘 다, 기본은 같은 머신.
3. **메시징**: 지금 Discord 유지 하에 사내 채팅을 언제 붙일지(Zulip/Mattermost) — 미국 채널만 Slack 브리지.

## 6. 첫 검증 (승인 시, 작게)

- 프로젝트 1개에 `DORI_HOME=~/projects/<x>/.dori`로 프로젝트 도리를 띄우고, 메인 도리에서 `dori remote add`(같은 머신은 ssh 대신 로컬 경로로도 가능한지 확인) 후 브리프 1건 전달 → 브랜치 회수까지.
- up.computer는 별도로 설치해 `dori acp` 등록 1회 검증.
