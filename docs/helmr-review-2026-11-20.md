# Helmr — 검토 단계 정리 (2026-11-20)

Lee: "일단은 검토만, UI도 넣어야 할 것 같은데" → **구현 착수 금지, 검토 문서만.** 단 UI는 필수 요구로 확정.

## 현재 확정된 구조 (검토안)

- **셸**: up.computer(MIT, T3 파생) — **포크하지 않고 upstream 그대로** 사용, `dori acp`를 ACP 프로바이더로 등록.
- **엔진/오케스트레이션**: dori (레인·브리프·리뷰 게이트·라벨 상태·ssh 원격).
- **Helmr**: 그 위의 **거버넌스 계층** — SOP 정의, 승인 게이트, 영수증·감사. UI도 여기에 속한다.
- **LoopForge의 개념**만 차용: `agent | script | approval` 노드. 서버 내장은 배제(상태 소유자 이중화).

## SOP 판단 UI — 무엇을 보여주고 무엇을 결정하나 (2026-11-20 요구 확정)

"SOP를 판단하는 UI"는 **진행 중인 SOP를 사람이 멈추고·승인하고·바꾸는 화면**이다. 화면 하나(Gate inbox) + 상세 하나(SOP run)로 시작한다.

### 목록 (Gate inbox)
- 대기 중인 게이트: `프로젝트 · 번들 · 노드 · 기다린 시간`
- 정렬: 오래 기다린 순, 위험 표시(범위 밖 파일 변경·검증 없음)가 있으면 위로

### 상세 (SOP run)
- **노드 체인**: `agent | script | approval` 상태(대기·실행·승인대기·완료·실패), 노드별 소요·비용
- **판단 근거**: 바뀐 파일 요약(diff stat), 번들 구성원(`Closes #N` + `Refs #…`), 실행된 검증(테스트 명령·결과), 실패 시 원문 로그
- **결정**: 승인 / 변경 요청(사유 필수) / 노드 건너뜀 / 여기서부터 재실행 / 중단
- **기록**: 모든 결정은 영수증(누가·언제·무엇·사유)으로 남고 다시 볼 수 있다

### 규칙
- **한 번들 = 한 게이트**: 번들 안 노드가 여러 개여도 사람이 결정하는 지점은 하나다. 그래야 MR 수만큼 판단이 늘지 않는다.

### 데이터 (dori 쪽)
- `$DORI_HOME/sops/<id>.json` — 노드 정의
- `$DORI_HOME/state/sop-runs.json` — 번들별 실행 상태·노드 이력
- `dori sop list|show|approve|reject|skip|rerun` — UI는 이 API만 읽고 쓴다(상태 소유자는 dori).

## UI가 필요한 이유와 범위

up.computer의 UI는 **채팅 + 워커 + 태스크**까지다. Helmr이 요구하는 화면은 그 밖에 있다:

| 화면 | 답하는 질문 | 데이터 |
|---|---|---|
| **Gate inbox** | "무엇이 내 승인을 기다리나" | 게이트 큐(레인 ready, PR, 정책 위반) |
| **Receipt/audit** | "누가 무엇을 승인했고 무엇이 반영됐나" | 영수증 원장 |
| **SOP editor/runner** | "이 작업을 어떤 순서·게이트로 굴리나" | SOP 정의 파일 |
| **Fleet** | "어느 머신이 무엇을 들고 있나" | 레인 + 원격 표 |

## UI를 어디에 두나 (3안)

1. **up.computer seam 확장** — human task(phase 0)·managed policy가 이미 자리. 가장 싸지만 upstream 변화에 종속.
2. **별도 Helmr 웹앱(ds-v4)** — 우리 토큰으로 게이트/영수증/SOP만. up.computer는 실행 셸로 병행. 독립성 최고, 표면 2개.
3. **하이브리드** — 실행·대화는 up.computer, 승인·감사는 Helmr 웹앱(딥링크로 연결). 권장.

## 결정 보류 항목

- Helmr을 제품명으로 확정하는가(현재는 코드네임).
- 첫 화면을 무엇으로: Gate inbox vs Receipt/audit.
- up.computer를 실제로 띄워볼지(설치·계정/페어링 조건 확인 필요 — 아직 미설치).
